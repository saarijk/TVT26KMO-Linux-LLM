Only Nginx (80) and SSH (22) are reachable from the internet. Ollama listens on 127.0.0.1 and the app has no TCP port at all, because Gunicorn uses a Unix socket. The cPouta security group also has no rule for ports 11434 or 8000.

3. Pipeline

  • Every push and pull request: the test job runs ruff check ., pytest (the model and database are mocked) and bash -n scripts/*.sh.
  • Push to main: the deploy job has needs: test, so it only starts when the tests are green. It rsyncs the code to /opt/chatapp/app and runs scripts/deploy.sh <sha> over SSH.
  • deploy.sh installs dependencies, applies the schema as root, installs the Nginx snippet (restoring the old one if nginx -t fails), installs and restarts only chatapp.service, and waits until the app reports the exact commit SHA.
  • Verification: the workflow then calls the public /viikko5/health and fails unless it returns github.sha. It also checks the chat page and static/app.js.

The SHA reaches the server as a command-line argument and is written to a REVISION file by the deploy, never by hand. A commit whose tests fail stops at the test job: the deploy job is skipped and the running version does not change.

SSH and the security group

GitHub's runners connect from changing IP addresses, so an allowlist would lock them out. I left port 22 open to 0.0.0.0/0. Risks: more bot login attempts, and the deploy key logs in as ubuntu, which has sudo, so a leaked key would give full control. Mitigations: password login is disabled (see below), the key is dedicated to deployment and can be revoked by removing one line from authorized_keys, and it is never committed.

5. How /viikko5/ was added to Nginx

The repository contains only location blocks in deploy/nginx/chatapp.conf, which the deploy copies to /etc/nginx/snippets/chatapp.conf. I added one line, include snippets/chatapp.conf;, to the existing site's server block. Nothing else in the site or in other sites was edited. The snippet uses location ^~, so regex locations from other weeks (such as the PHP one) cannot capture /viikko5/static/app.js. The deploy runs nginx -t before reloading and restores the previous snippet on failure.

8. Week 4: is the chat database replicated to server B?

Yes. Server A's binary log has no Binlog_Do_DB filter and server B has no Replicate_Do_DB filter, so every database on A is copied, including chatapp. It is harmless: B is read-only for users, the replication thread is not blocked by that, and the chat app runs only on A. The chat messages are therefore also stored on B.

10. A problem I solved

Symptom: after the reboot test, /viikko2/ returned 502 Bad Gateway while the new chat worked.
Diagnosis: systemctl status week2 and journalctl -u week2 -b showed "Can't connect to MySQL server ... Connection refused", followed by "Start request repeated too quickly".
Cause: since Week 4 the Week 2 app connects to MariaDB as soon as it starts, but its unit only had After=network.target. At boot it started before MariaDB, crashed five times in under a second, and systemd gave up.
Fix: a drop-in override that starts it after MariaDB and retries slowly, leaving the original unit file untouched.
Lesson: a reboot test is worth doing for the old services too, and a service that depends on a database needs explicit ordering and a sensible restart delay.
